# Read-only local Codex thread inventory

Use `npm run codex:threads` from the repository root on the owner's Omarchy workstation. On another host, pass an exact absolute Codex executable path after `--codex`. The command starts a short-lived local Codex App Server process, initializes the protocol, calls only `thread/list` for up to 25 recent CLI, VS Code, or App Server threads, and exits. It does not start or resume a thread, read prompts or turn items, send a model request, or dispatch a Switchyard chord.

The output contains exact thread IDs and **runtime state as seen by that short-lived App Server process**. `not-observed` means the saved thread was not loaded in this observer; it does not mean the task finished or that another Codex app is idle. `idle`, `active`, `waiting-on-approval`, and `error` are likewise local runtime observations, not companion-verified Switchyard task outcomes. Thread titles and previews are discarded. The first host probe returned 25 recent threads, all `not-observed`; no live session or provider capability has been promoted from this inventory.

Official [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server) specifies `thread/list`, `thread/read`, runtime `status`, and the initialization handshake. It also documents `thread/status/changed` for a connected client. The local binding below records an exact thread ID, task ID, repository, and optional authenticated target. A future provider adapter still needs authoritative task lifecycle evidence before reporting blocked or finished. A separate native ChatGPT desktop window remains unknown without its own supported observation path.

## Live local daemon snapshot

On Linux, `npm run codex:live` connects to the **already-running** current-user Codex App Server control socket through its documented Unix WebSocket transport. It checks socket ownership and mode, initializes the protocol, requests at most 25 recent threads, and disconnects. It does not start a daemon, resume a thread, submit a turn, read prompts, or register a Switchyard session. An optional `-- --socket ABSOLUTE_PATH` selects a reviewed local test socket. If the daemon is absent or the socket is not private, it exits with an error.

This snapshot can show `active`, `waiting-on-approval`, and `idle` for threads loaded in that daemon. The observed runtime status is **not** a verified Switchyard task outcome. In particular, `idle` is not `verified_finished`, and `waiting-on-approval` is not automatically a Switchyard `verified_blocked` queue entry. The VS Code **Show Managed Sessions** picker adds local Codex rows beneath the authenticated companion rows and does not promote their runtime status into the protected registry or blocked/finished queues.

## Start a task-bound local Codex thread

On Linux, open an exact Git repository root in VS Code and run **SXSY-B122: Start Task-Bound Codex Thread** from the Command Palette. Select a root if the window has several, then enter one short opaque task ID. The extension calls App Server `thread/start` with that root, then persists a short assistant binding marker with `thread/inject_items` so the thread can resume. This creates no user prompt or model turn. It saves exactly the thread ID returned by Codex and opens `codex resume --remote unix:// <thread-id>` in a VS Code terminal. The executable is the owner's installed mise Codex path; the launch uses fixed arguments and no shell. If a unique authenticated Codex session already reports the same task and root with a complete TargetSnapshot ID before and after thread creation, that target is copied into the local binding. Otherwise the target is explicitly `unverified`.

Bindings are one file per Codex thread under `${XDG_STATE_HOME:-$HOME/.local/state}/strathex-switchyard/codex-bound-threads`, with a private directory and `0600` files. The store is capped at 64 bindings; it contains thread ID, task ID, repository root, optional exact target, companion session ID, and creation time. It contains no prompts, turns, code, or credentials. **Show Managed Sessions** reads each saved thread by exact ID and joins its local runtime status to the binding. A thread absent from the recent 25-thread page can still show live status. If an exact read fails, the bound thread appears as `not-observed`, not finished. A matching companion registration, when available, remains `Registered` only; this local observation does not prove `Observable`, `Mediated`, `verified_blocked`, or `verified_finished`.

The existing Windows managed-terminal launcher is separate and still starts its pinned CLI without a Codex App Server thread ID. This Linux command adds no B122 chord or Windows keyboard configuration. A versioned native provider adapter and authoritative target/lifecycle proof remain open.
